Cómo cumplimos cada entregable

Metamorfosis · Ingeniería de Software II · Universidad de los Llanos · noviembre de 2026
Primera parte: qué pedía el profe y cómo lo hicimos. Segunda parte: guía para mostrar cada ítem en vivo en la sustentación.

En una frase: Metamorfosis es una app web y una app Android (APK) para seguir metas. Cada meta tiene un camino con hitos (pasos que se logran una vez) y hábitos (cosas que se repiten ciertos días). Web: metamorfosis-mu.vercel.app · Servidor: metamorfosis-api.onrender.com · Base de datos: Supabase (PostgreSQL).

Primera parte · Qué hicimos

Web y móvil. Web: la app React se abre en cualquier navegador y se adapta al tamaño de la pantalla. Móvil: una APK de Android hecha con Capacitor, que mete esa misma app React dentro de una app nativa: se instala, tiene ícono y habla con el mismo servidor. GitHub Actions la compila sola y la prueba en un emulador de Android 14.

Documento: sección 3.2.

Dos niveles (dos capas). El cliente (React, publicado en Vercel) y el servidor (API en Java con Spring Boot, publicada en Render) corren en máquinas distintas. La base de datos PostgreSQL está en Supabase y solo el servidor la toca; el cliente le pide todo al servidor por HTTPS.

Documento: sección 3.

ORM. Usamos JPA / Hibernate: cada tabla es una clase Java con @Entity (Meta, Usuario, SubMeta…), y los repositorios heredan de JpaRepository, así que no se escribe SQL para guardar o buscar. Flyway crea y cambia la base con 28 migraciones (V1 a V28). El diccionario de datos y el modelo entidad-relación se generaron con comandos desde la base real: 14 tablas, 109 columnas, 14 llaves foráneas.

Documento: sección 4 (4.4 diccionario de datos, 4.5 modelo E-R en Mermaid).

Web services. El servidor ofrece una API REST en JSON, protegida con token JWT (la usan la web, la APK y Postman), y consume un web service externo: la API REST de Brevo (POST https://api.brevo.com/v3/smtp/email), con la que manda los correos de registro, invitación, código para recuperar la contraseña y aviso de cambio de contraseña.

Documento: sección 5. Código: backend/.../service/correo/BrevoCorreoService.java.

Accesibilidad y usabilidad mayor a 70. Accesibilidad: PageSpeed Insights (herramienta en línea de Google) sobre la app publicada: 100 en celular y en computador. Usabilidad: cuestionario SUS respondido en línea (Google Forms) por 5 personas: 83,0 sobre 100. Complemento: el botón de accesibilidad Sienna (abajo a la izquierda) y, para el equipo, eslint-plugin-jsx-a11y.

Documento: sección 6 (6.1, 6.2 y 6.3).

Minificar y ofuscar. Al construir (npm run build) Vite minifica el código y javascript-obfuscator lo ofusca: nombres cambiados y textos escondidos en una tabla codificada. No se publican source maps. El JavaScript pasa de 1,9 MB a 1,1 MB y no se puede leer.

Documento: sección 7.

Reportes y gráficas. Mi reporte tiene cuatro gráficas hechas con Chart.js (cumplimiento general, por tipo, por plazo y estado, y cumplidas por mes), cada una con Ver datos en tabla. Cada hábito tiene además sus estadísticas: constancia, rachas, gráfica por día, semana o mes, e historial.

Documento: sección 8.

Logs. Log de auditoría: la tabla log_actividad guarda cada acción (CREAR_META, INICIAR_SESION…) con EXITO o ERROR; no se puede borrar ni modificar. Log de aplicación: los eventos técnicos del servidor, que en producción se ven en la pestaña Logs de Render (en local, en el archivo metamorfosis.log, que rota a los 10 MB y guarda 14 días).

Documento: sección 9.

Evidencia de pruebas. Caja blanca: 302 pruebas JUnit y Mockito en 36 clases, 0 fallos, cobertura JaCoCo de 78 % de instrucciones. Caja negra: colección de Postman con 162 peticiones y 291 aserciones, 0 fallos (con Newman). Frontend: 52 pruebas con Vitest, 0 fallos. Integración: flujos completos por HU.

Documento: sección 10 y el plan de pruebas de cada HU (sección 16).

Internacionalización. La app está en español e inglés: selector ES · Español / EN · English. También salen en el idioma elegido los mensajes del servidor y los correos.

Documento: sección 11.

Manual técnico y de usuario. Dos manuales en PDF, con portada, índice y capturas: el de usuario (25 páginas, con el texto exacto de cada botón) y el técnico (18 páginas: arquitectura, código, base de datos, API, seguridad, despliegue y APK).

Documento: sección 12. PDF en la carpeta de Drive del proyecto y en docs/Manuales del repositorio.

Segunda parte · Guía para mostrarlo en vivo

Antes de entrar (10 minutos antes).
  1. Despertar el servidor: abrir https://metamorfosis-api.onrender.com/api/metas. Render apaga el servidor sin uso y tarda cerca de un minuto en despertar. Cuando muestre un JSON con «Autenticación requerida», ya está listo.
  2. Pestañas abiertas: la app (metamorfosis-mu.vercel.app) con la sesión iniciada en una cuenta que ya tenga metas, algunas cumplidas y hábitos con días registrados; el panel de Vercel (Felipe); el panel de Render (Samuel); Supabase → Table Editor; Postman con la colección importada; pagespeed.web.dev; el repositorio en GitHub; la carpeta de Drive con los manuales; y este documento.
  3. Celular de Daniel con la APK instalada y la sesión iniciada en la misma cuenta.
  4. No mostrar contraseñas ni claves: en Render y Vercel, las variables con claves (contraseña de la base, BREVO_API_KEY, secreto JWT) se dejan ocultas.

1. Evidencia de pruebas

Mostrar las pruebas corriendo en vivo contra el servidor real (Postman):

  1. En Postman: Import → docs/Pruebas/postman/Metamorfosis.postman_collection.json y docs/Pruebas/postman/produccion.postman_environment.json.
  2. Arriba a la derecha elegir el entorno Metamorfosis producción (Render).
  3. En la colección, abrir la carpeta Seguridad · rutas protegidas → Run → Run Metamorfosis. Resultado: 8 peticiones y 16 pruebas en verde, todas contra metamorfosis-api.onrender.com (lo comprobamos el 17 de noviembre).
  4. Abrir una petición, por ejemplo Mis metas sin token, y mostrar la pestaña Tests (lo que se comprueba) y la respuesta 401.

Después mostrar los resultados completos: sección 10 del documento, con Newman (162 peticiones, 291 aserciones, 0 fallos), mvnw verify (302 pruebas, 0 fallos) y el informe de JaCoCo (78 %). Si el profe pide ver otra corrida: en la carpeta frontend, npm test corre las 52 pruebas de Vitest en segundos.

«La colección completa crea sus propios usuarios de prueba, por eso la corremos contra una base local; contra producción corremos la carpeta de seguridad, que no deja datos.»

2. Dos capas (cliente en Vercel y servidor en Render)

La prueba más fuerte: que el navegador habla con otro servidor.

  1. En la app (metamorfosis-mu.vercel.app) presionar F12 → pestaña Red (Network) → en el filtro escribir onrender.
  2. Crear una meta (+ Nueva meta → Crear meta). Aparece la petición POST https://metamorfosis-api.onrender.com/api/metas con estado 201. Clic en ella → Respuesta: el JSON de la meta que devolvió el servidor. En Encabezados se ve Authorization: Bearer … (el token JWT).
  3. En Supabase → Table Editor → tabla meta, ordenar por codigo_meta de mayor a menor: ahí está la fila que se acaba de crear. El cliente nunca tocó la base: lo hizo el servidor.
  4. Abrir en otra pestaña https://metamorfosis-api.onrender.com/api/metas: responde un JSON con «Autenticación requerida». Es otra máquina, con su propia seguridad.

Dónde está configurada la conexión:

  • Vercel (cuenta de Felipe) → proyecto → Settings → Environment Variables → VITE_API_URL = https://metamorfosis-api.onrender.com: el cliente sabe a qué servidor llamar.
  • Render (cuenta de Samuel) → servicio metamorfosis-api → Environment → APP_CORS_ALLOWED_ORIGINS = https://metamorfosis-mu.vercel.app (el servidor solo acepta peticiones de ese cliente) y SPRING_DATASOURCE_URL apuntando a Supabase (sin mostrar la contraseña). En Logs se ve el servidor funcionando en ese momento.
  • En el código: frontend/src/services/*.js usan import.meta.env.VITE_API_URL; nada de la base de datos está en el frontend.
«Son tres lugares distintos: Vercel sirve la interfaz, Render ejecuta la API en Spring Boot y Supabase guarda los datos. Si apagáramos Render, la página cargaría pero no podría iniciar sesión ni mostrar metas.»

3. ORM

  1. Documento, sección 4: tabla de entidades (4.2), ejemplo de mapeo (4.3), diccionario de datos generado por comando (4.4) y modelo E-R en Mermaid (4.5).
  2. En GitHub abrir backend/src/main/java/com/metamorfosis/backend/model/Meta.java: @Entity, @Table(name = "meta"), @Id, @ManyToOne al creador, @Enumerated para tipo, plazo y estado, @OneToMany a las sub-metas.
  3. Abrir repository/MetaRepository.java: extends JpaRepository<Meta, Integer> da guardar, buscar y borrar sin SQL; las consultas especiales están en JPQL, sobre las entidades.
  4. application.properties: spring.jpa.hibernate.ddl-auto=validate (Hibernate comprueba que las clases coinciden con la base) y spring.flyway.enabled=true.
  5. En Supabase → tabla flyway_schema_history: las 28 migraciones aplicadas.
«El diccionario no se escribió a mano: lo sacamos de la base con pg_dump y con un script que consulta el catálogo de PostgreSQL (docs/BaseDeDatos/generar.py).»

6. Ofuscación

  1. En la app publicada presionar Ctrl + U (ver código fuente) y hacer clic en el enlace /assets/index-….js.
  2. Se ve todo en una sola línea, con funciones como var e=B;(function(e,t){…parseInt(n(4716))…: los nombres originales y los textos ya no existen, están en una tabla codificada.
  3. F12 → pestaña Fuentes (Sources): solo aparece la carpeta assets; no hay carpeta src ni archivos .map, porque los source maps no se publican.
  4. Configuración: frontend/vite.config.js (plugin de javascript-obfuscator y sourcemap: false). Tabla de tamaños en la sección 7 del documento.

7. Gráficas e informe (Reporte)

  1. En la app tocar Reporte en el encabezado → pantalla Mi reporte.
  2. En Tipo de reporte pasar por los cuatro: Cumplimiento general, Cumplimiento por tipo de meta, Metas por plazo y estado y Metas cumplidas por mes.
  3. Tocar Ver datos en tabla: los mismos números en una tabla (accesible para lectores de pantalla).
  4. Extra: en Tu camino, tocar el nombre de un hábito → sus estadísticas (Últimos 7 días, Racha actual, gráfica con Agrupar por día, semana o mes, Historial).
La cuenta que se use debe tener metas cumplidas en meses distintos; si no, las gráficas salen vacías. Prepararla antes.

8. Web service (correo con Brevo)

  1. Explicar: el servidor consume la API REST de Brevo. Al mandar un correo hace POST https://api.brevo.com/v3/smtp/email con la cabecera api-key y un JSON con destinatario, asunto y HTML. Código: backend/.../service/correo/BrevoCorreoService.java (usa RestClient de Spring).
  2. Demostrarlo sin tocar datos: cerrar sesión → Iniciar sesión → ¿Olvidaste tu contraseña? → escribir el correo de la cuenta → Enviar código. En segundos llega al correo el código de 6 dígitos (no hay que usarlo). Otra opción: invitar a alguien a una meta con Invitar personas.
  3. Si se tiene abierta la cuenta de Brevo del proyecto: Transactional → Logs muestra el correo recién enviado.
  4. Además el servidor ofrece su propia API REST: es la que se vio en Postman (punto 1) y en la pestaña Red (punto 2).

10. Logs

  1. Auditoría en vivo: hacer una acción en la app (crear o editar una meta) y otra que falle (iniciar sesión con la contraseña equivocada, una sola vez).
  2. En Supabase → Table Editor → log_actividad, ordenar por fecha_hora de más nueva a más vieja: aparecen las dos filas, por ejemplo CREAR_META · EXITO e INICIAR_SESION · ERROR, con usuario, entidad, fecha y detalle.
  3. Log de aplicación: Render → servicio metamorfosis-api → Logs: arranque de Spring Boot, Flyway y avisos del servidor en tiempo real.
«La tabla de auditoría solo admite insertar: un trigger impide editar o borrar filas.»
